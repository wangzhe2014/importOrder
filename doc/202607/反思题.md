# 反思题

## 1. 为什么 V2 下单导入链路不能继续采用同步阻塞方式？什么时候同步反而更简单可靠？

V2 导入链路包含文件解析、规则执行、SKU 校验、重复检查、批量写库、错误记录和进度反馈。10,000 行文件如果放在一次 HTTP 请求内同步执行，会同时占用 Serverless 执行时间、内存、数据库连接和用户等待时间，容易出现 504、连接池耗尽、用户重复上传和失败不可恢复等问题。

异步任务化后，上传请求只负责创建任务并返回 `task_id`，耗时处理由 Worker 承接，失败可重试，进度可查询，错误可定位，更符合大文件和大促场景。

同步方式在小数据量、低频、强一致交互场景下仍然更简单可靠。例如单条运单保存、规则 CRUD、少量数据预览校验等，用户需要立即知道结果，且处理时间稳定在几百毫秒内。这类场景引入队列反而会增加状态管理和排障成本。

## 2. 处理单元变大或变小，会分别带来什么影响？

处理单元变大时，队列消息数量减少，调度开销和批次聚合开销降低，单次数据库批量写入也更充分。但它会增加单个 Job 的执行时间、内存占用和失败重试成本；一个批次失败时，需要重跑更多行，卡死恢复的影响面也更大。

处理单元变小时，失败隔离更细，进度变化更频繁，重试成本更低，也更容易横向扩展。但队列消息、状态更新、性能日志、数据库往返次数都会增加，过小会让调度和日志开销超过业务处理本身。

本项目默认 `1000 行/批`，10000 行拆成 10 个处理单元。这个粒度在实测中能兼顾吞吐、失败隔离和数据库压力。

## 3. 如果吞吐目标从 10,000 单/分钟提升到 50,000 单/分钟，最先成为瓶颈的是 Worker、Redis 队列还是数据库写入？你会如何扩展？

最可能先成为瓶颈的是数据库写入，其次是 SKU 校验查询和 Storage/解析链路。Redis 队列本身通常不是第一瓶颈，因为队列只负责分发消息，真正耗时集中在解析、校验和 UPSERT。

扩展思路：

1. 将 Worker 水平扩容到多实例，并通过 `WORKER_CONCURRENCY` 控制每个实例并发，避免打满数据库连接池。
2. 将 SKU 校验前置为任务级一次查询或缓存预热，减少重复查询。
3. 将写入从普通 UPSERT 进一步优化为临时表 + merge、COPY 或数据库 RPC 批量写入。
4. 按业务键或任务维度分片，避免大量批次同时写同一热点索引。
5. 对 `batch_performance_log`、`trace_events`、`import_task_errors` 做冷热分层，避免观测日志反向拖慢主链路。
6. 将 Worker 部署到靠近 Supabase 数据库和 Storage 的区域，减少网络往返。

如果目标提升到 50,000 单/分钟，需要先用压测定位当前 `insert_duration_ms`、SKU 查询耗时和 DB CPU/IO，再决定是扩 Worker、扩数据库规格还是改写入方式。

## 4. 如果队列消息重复投递，为什么“业务幂等”比“消息只投递一次”更重要？

分布式系统里严格的“只投递一次”很难保证。网络超时、Worker 崩溃、确认消息失败、Outbox 重放都可能导致消息被重复消费。强行依赖队列只投递一次，会把正确性押在基础设施行为上，一旦出现边界情况就可能重复入库或重复累计进度。

业务幂等更可靠。本项目通过 `claim_batch` CAS 认领批次，确保同一个 `task_id + unit_id` 不会被多个 Worker 同时处理；通过 `complete_batch` 从批次账本重算任务聚合值，避免重复累计；通过 `external_code + sku_code + line_no` UPSERT，避免重复写入运单。即使队列重复投递，业务结果仍然稳定。

## 5. 如果某个处理单元中有部分行失败，应该整体回滚还是成功行先入库？为什么？

本项目选择成功行先入库，失败行进入 `import_task_errors`，任务最终状态为 `partial_success`。

原因是导入文件里的错误通常是行级数据问题，例如非法 SKU、必填字段缺失、电话格式错误。让一行坏数据导致 999 行好数据整体回滚，会降低业务吞吐，也增加用户修复成本。成功行先入库可以让有效订单继续流转，用户只需修复失败明细中的具体行。

整体回滚适合强事务业务，例如财务凭证、库存扣减必须保持整单原子性。本次 V2 导入链路的考核目标更偏批量下单和错误可修复，因此部分成功更符合业务效率。

## 6. 错误明细中需要保留原始值，但手机号和地址属于敏感信息，如何平衡排障效率和数据安全？

原则是只保留排障所需的最小信息，不在错误表中保存完整敏感值。

本项目对错误原始值做脱敏：手机号保留前三位和后四位，中间用 `****`；地址只保留前六位和后四位。错误明细仍能让用户判断是哪一行、哪个字段、哪类格式问题，但不会泄露完整手机号和地址。

进一步的生产策略包括：

1. 错误明细设置保留周期，到期归档或删除。
2. CSV 导出受权限控制，并记录审计日志。
3. Trace 和服务端日志不打印完整上传内容。
4. 对 service role key、数据库连接串、队列连接串只使用服务端环境变量，不进入 Git。

## 7. 如果 Outbox 表持续增长到千万级，如何清理、归档和设计索引？

Outbox 表是可靠投递的运行账本，不应无限增长。清理策略应按状态和时间分层：

1. `sent` 且超过保留期的数据定期归档到冷表或对象存储，再从热表删除。
2. `failed` 保留更长时间，供运维排查；超过阈值后进入死信归档。
3. `pending` 和可重试 `failed` 保持在热表，并设置明确告警。

索引设计上，热路径需要覆盖 dispatcher 查询：`status + next_retry_at + created_at`。按 `aggregate_id` 或 `trace_id` 查询时，需要独立索引。数据量达到千万级后，可以按 `created_at` 月份分区，热分区保留最近数据，历史分区只读或归档。

清理任务必须小批量执行，避免一次性 delete 锁表。生产上还需要监控 Outbox 积压量、最老 pending 时间和 failed 数量。

## 8. 如果 AI 生成的解析规则导致大量字段映射错误，监控系统如何帮助快速发现是规则问题而不是数据库问题？

规则问题和数据库问题的观测特征不同。

如果是 AI 生成规则映射错误，通常会表现为：

1. `parse_duration_ms` 和 `rule_duration_ms` 正常，但 `validate_duration_ms` 后错误数量激增。
2. 错误集中在 `E002` 必填缺失、`E003` 电话格式错误、`E004` 数量错误，且字段分布高度集中。
3. `insert_duration_ms` 不高，因为大量行在写库前已失败。
4. Trace 中批次正常开始和结束，没有数据库写入异常。

如果是数据库问题，通常会表现为：

1. `insert_duration_ms` 明显升高或批次系统级失败。
2. 错误集中在 `E007` 数据库写入失败。
3. 多个任务同时变慢或失败，而不是某一个规则对应的任务失败。
4. 队列积压上升，慢批次 TOP10 集中在写入阶段。

因此监控看板需要同时展示错误分布、字段分布、阶段耗时和 Trace 时间线。运维可以在 1 分钟内判断问题发生在规则映射、数据质量、SKU 主数据还是数据库写入层。
